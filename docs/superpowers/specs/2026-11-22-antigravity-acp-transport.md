# Antigravity bridge: ACP transport

Date: 2026-11-22. Issue: [#11](https://github.com/mubeda/agent-bridges/issues/11). Plugin version 0.2.0.

## Problem

The `antigravity` companion drove Antigravity by running `agy` in print mode, one process per prompt, with flags for the model, the effort, a JSON schema and a settings file whose deny rules made a run read-only. The bridge now uses Antigravity's ACP server (`agy acp`) instead. One process holds one session, and the bridge sends the prompts and reads the answer as protocol messages. This note records what was probed, how a read-only run is made safe without the print-mode deny rules, and what the bridge does not support.

## Probed facts (agy 1.5.14, 2026-11-22)

- `agy acp` is a stdio server: one JSON-RPC 2.0 object per line. Its flags include `--add-dir <dir>` (repeatable), `--agent <name>`, `--dangerously-skip-permissions`, `--log-file` and `--login`. It has no `--settings`, `--model`, `--effort` or `--output-format` flag. Global flags placed before `acp` do not reach the session.
- The client sends numeric request ids. The server's own requests (`session/request_permission`) carry string ids such as `"1"`, and the reply uses the same id value.
- `initialize` (protocol version 1, no client `fs` or terminal capability) returns `agentCapabilities` with `loadSession: true` and `sessionCapabilities` `resume`, `close`, `load` and `list`. The cached Google sign-in is used without an `authenticate` call. Without credentials a request fails with code `-32000`, "Authentication required" (from Google's ACP page; not reproduced).
- `session/new` with `cwd` and `mcpServers: []` returns `sessionId`, `models.availableModels` (the same ids as `agy models`), and the config options `model`, `thought_level` (`low`, `medium`, `high`, `xhigh`) and `mode`.
- `session/set_model` accepts a full model id. `session/set_config_option` with `configId: "thought_level"` sets the thinking level.
- `session/prompt` streams `session/update` notifications. Answer text is in `agent_message_chunk`. Tool use shows as `tool_call` (with `name`, `kind`, `status`) and `tool_call_update`. The response is `{stopReason, usage}`.
- A shell command triggers `session/request_permission` with an `allow_once` and a `reject_once` option. After a refusal the turn can end `end_turn` with no answer text.
- A file write is never asked, inside or outside the workspace. Mode `plan` does not stop it. Declaring client `fs` capabilities does not route writes through the client.
- A headless session cannot name its own model.
- An agent file with `tools: []` gives an agent whose only tool is the built-in `manage_task`; it could not read a file. A made-up tool name makes the agent fail to start ("tool ... not found in registry").
- `session/set_model` takes effect: the next turn's `config_option_update` showed the requested family and thinking level.
- `session/resume` with an id the server does not have answers error `-32603`, "Failed to read session <id>; retry, or load it with session/load". `session/load` with such an id succeeds and silently creates a new session under that id, so the bridge never calls `session/load`.

## The read-only guard

In ACP, permission prompts and modes do not stop writes. The one guard that holds is an agent with a restricted tool list: no tools at all for a review, file reading only for a read-only task. Such an agent is defined in a plugin under a folder passed with `--add-dir`, and the session is started with `--agent <name>`.

For every review, and every task without `--write`, the companion does the following:

1. It writes a fresh folder under its state root, `<state>/readers/reader-*`, mode 0700, with an ownership marker file `.agent-bridges-reader`. The state path is compared with the workspace by canonical path (symlinks resolved on the nearest existing folder) and whole path components, so a symlink or a folder named `..state` inside the workspace is caught. If the folder would fall inside the workspace, the run fails with a message and nothing is written: there is no fallback location (a temp folder can be project-local too). The folder holds `.agents/plugins/agent-bridges-reader/.antigravity-plugin/plugin.json` and `agents/<name>/agent.md`, with a random agent name. A review's agent has `tools: []`; a read-only task's has `tools: [read_file]`.
2. The agent body holds a random 128-bit token and tells the agent to give it back when asked.
3. It starts `agy acp --add-dir <folder> --agent <name>`.
4. Its first prompt is "Reply with only your agent token." A name that Antigravity does not recognise falls back silently to the default agent, which has every tool, and `session/new` looks the same either way. The real reader has the token in its instructions and needs no tool, so the turn fails if any `tool_call` (even `read_file` or `manage_task`) or any permission request comes during it, and the answer must equal the token after trimming. When the check fails, the companion cancels, ends the process tree and fails the run: "the restricted reader was not in effect … nothing was reviewed".
5. It refuses every permission request and records it in `deniedActions`. If a turn then ends with no text, one follow-up asks the agent to answer from what it has read. The setup requests and the token check time out after 60 seconds; the real prompt has none.
6. A `tool_call` outside the agent's own tools is a violation: anything but `manage_task` in a review, anything but `read_file` or `manage_task` in a task. A call with no name counts too. The rule holds for the whole read-only session, including an update that arrives in the same chunk right after a prompt's response; the run is checked again after every prompt and before it reports success. The companion sends `session/cancel`, fails the run, and does not show the answer. Answer text only counts while its turn is open.
7. It removes the folder at the end, on a forwarded signal (on every platform, even when ending the process tree fails), and on `cancel` from another process (the job record stores the path). It removes a folder only when its canonical path sits directly in this workspace's reader root and it carries the marker, so a stale or edited record cannot point the removal elsewhere.

The token check proves that Antigravity loaded the agent file. It does not prove that Antigravity enforces the agent's tool list. That enforcement was observed by probe on agy 1.5.14 (an agent with `tools: [read_file]` could not write or run a command; one with `tools: []` could not read a file), and the client's tool-call rule in step 6 is the second line of defence.

Permission requests are answered only with the exact one-time kinds: `reject_once` in a read-only run, `allow_once` in a write run. An `allow_always` or `reject_always` choice could save a rule in the user's Antigravity settings, so it is never picked. When the exact one-time kind is not offered, the request is answered `cancelled` and the run fails with a message that the server offered no one-time choice.

Write runs (`task --write`, `transfer --write`) start `agy acp` with no `--agent` and allow every permission request. They never pass `--dangerously-skip-permissions`.

## Results

The answer is the concatenation of `agent_message_chunk` texts of the last prompt. A stop reason other than `end_turn` fails the run, and the error names the reason. Reviews carry the JSON schema in the prompt. The answer is checked by hand against the schema's required fields, types and values; an answer that fails gets one follow-up asking for the object only. If that also fails, the plain text is shown with "No structured result came back from Antigravity." Reviews have no tools, so the prompt holds the whole evidence: the git status, the staged, unstaged or branch diff, and the contents of untracked text files (each up to 24 KiB, symlinks never followed), at most 256 KiB. The budget is kept while collecting: each git command is read only up to the bytes left (git is stopped beyond that, so a huge binary patch gives a cut review, not a buffer error), and untracked files are no longer read once the budget is used. Files are ordered so the most useful part survives a cut: source first, then tests, then generated or vendored files, shallower paths before deeper ones. A diff whose `index` line (old and new blob hashes) equals one already shown, or an untracked file with the same content, is only named as identical to the first, so a synced copy does not double the evidence. When the budget runs out, a note lists the files not shown and the reviewer is told to say the rest was not reviewed. The old "self-collected" mode, where the reviewer read the changed files itself, is gone. Everything is mapped onto the shape the companion stored before, so rendering, `result` and job records are unchanged.

Only a write run continues a session, and only the most recent finished task, when it was a write task whose prompt reached its session (`agyPromptSent`). A run that failed before its prompt (an unknown model, a setup timeout) holds an empty session, so it is not continuable. When the most recent task cannot be continued, a write `--resume-last` starts a new session with a warning that says why; it never jumps back to an older write session, which the user may not mean. `--resume-job <job-id>` (write runs only) continues exactly that job after checking it is still continuable, and otherwise fails before anything runs; `/antigravity:rescue` passes the job the user confirmed this way, so a job that finishes while the question is open cannot take its place. `task-resume-candidate --for-write` reports the same most recent job when it is continuable. A write resume uses `session/resume` only. An error whose message says "Failed to read session" is a missing session: a new session starts with the existing warning. Any other error fails the run and the prompt is not sent. When the server does not offer `session/resume`, a write resume starts a new session with a warning that this Antigravity version cannot continue sessions.

A read-only run never resumes an earlier session. A smoke run on 2026-11-22 showed that a resumed session keeps the agent it was created with: a read-only `--resume-last` after a write session got the full-tool agent, which started `run_command` before the tool guard stopped it, and a file write (never asked) could have happened first. So a read-only run with a resume request starts a fresh reader session with the token check, sends no `session/resume` or `session/load`, and warns: "A read-only run cannot continue an earlier Antigravity session, because the restricted reader cannot be attached to it; this started a new session. Add --write to continue the earlier one." The new session id is stored as usual.

The reverse case was also seen in a smoke run: a write `--resume-last` after a read-only task resumed the reader session and answered "I am a read-only assistant", with no file written and exit 0. So every job record now carries `agyReadOnly` (true for a review or a task without `--write`), and a write resume never sends `session/resume` with a reader session's id. When the most recent task was read-only, it starts a new write session and warns: "The earlier Antigravity session was read-only and cannot be continued with write access; this started a new session." A record without these fields was written by 0.1.x, whose print-mode runs had the full agent and always received their prompt, so it counts as continuable. Without `--for-write`, `task-resume-candidate` reports no candidate, since a read-only run never continues one.

## Transport failures and cancel

A request fails when its line cannot be written (input closed, or a write error), when the server's output ends before the answer, when the process exits, and when the server sends an error with a null id. A response whose id is a numeric string matches its numeric request. Lines that are not JSON are skipped (the server may log) and kept in the error text shown on a failure.

`cancel` first creates a marker file `<job>.cancelled` next to the job record, before it reads or signals anything. A file cannot be overwritten by a job update, so the marker wins every race: a worker that sees it never starts `agy`, and a worker, a finishing run or a signal handler that sees it writes only the handles cancel needs (agy's pid, the reader folder) and never a status. `cancel` then marks the job `cancelling`, keeping `pid`, `agyPid` and `readerDir`, ends the processes, removes the reader folder, reads the record again for handles a worker recorded in the meantime, and only then writes `cancelled` without the handles. If the teardown is interrupted, the job stays `cancelling` with its handles, and a second `cancel` retries it.

After the final answer the companion keeps reading `agy`'s output until it closes (or briefly after the process tree was ended), then checks the guard again: a forbidden tool call that arrives in a later chunk still turns the run into a failure before anything is stored or printed. A read-only security stop ends the tree at once, with no grace period. A forwarded signal fails the run immediately, so a turn that finishes during the teardown is neither stored nor printed. Any failure after `agy` started (a bookkeeping write included) fails the run and ends the tree. At the end the child's pipes are destroyed and the child is unreferenced, so a descendant that kept a pipe open cannot keep the companion alive.

## Not supported

- **API keys.** Only the Google sign-in cached by `agy` works. The `-32000` error maps to "not signed in: run `agy` once interactively, or `agy acp --login`". Setup no longer reports a key.
- **Structured output by a schema flag.** ACP has none; the prompt asks for JSON instead.
- **Effort `max`.** The server offers four thinking levels. `max` is rejected before any job is written.

## Residual risk

- A write task allows every permission request, and file writes are never asked in the first place, so a write run can change anything the user can.
- A review has no tools. It sees only the evidence in its prompt, at most 256 KiB, so the end of a larger change is not reviewed; the prompt names the files left out and tells the reviewer to say so. The identical-copy rule compares blob hashes, so it only skips content that is byte-for-byte the same as a change already shown.
- The token check proves that the reader's definition reached the session. A default agent that read the agent file to find the token would make a tool call during the check, which fails it.
- A real permission prompt for a command is normally preceded by a `tool_call` for that command. In a read-only run that `tool_call` already stops the run, so the refusal-and-follow-up path is a second line of defence that rarely runs.
- This applies to read-only tasks only (reviews have no file tool): the task's reader can read any file the user can read when it is given an absolute path; the print-mode read-only run could not read outside its workspace. So a task over untrusted content could be led to quote another file into its answer, and the model provider receives whatever the reader reads. The reader has no shell and no web tool, so that text reaches only the calling session and the provider.
- The 60-second limit covers setup and the token check only; a real prompt that never ends is ended by `cancel` or a signal.
- `session/cancel` is best effort. A `cancel` from another process cannot reach the session, so it ends the process tree directly, as before.
