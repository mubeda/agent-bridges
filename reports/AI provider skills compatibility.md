# Fix three CLI breaks before OpenCode 2.0 lands

agent-bridges is mostly compatible with every host it targets, but **four backend invocations break on current installs (OpenCode V2 is now the default install)**, and those need fixing before anything else. The OpenCode bridge builds `opencode run --format json --dir <cwd> ... --variant <effort>`, and on OpenCode V2 (v2.2.6, the current V2 release) both `--dir` and `--variant` are unrecognized flags, so every OpenCode review, rescue and delegate run fails at argv parsing. Transfers into OpenCode call the top-level `opencode import`, which V2 moved to `opencode session import`. The Claude bridge passes a schema *file path* to `claude --json-schema`, which accepts only inline JSON, so structured Claude reviews fail. The Gemini bridge appends `--include-directories` to `agy` runs even though Antigravity's flag is `--add-dir`. The installer has a quieter problem too: it copies each plugin tree, `package.json` included, into OpenCode's `plugins/` directory, which V2 now auto-loads as V2 plugin packages, and it writes commands and agents into the singular `command/` and `agent/` directories that V2 treats as legacy. The manifests are in good shape. The `.claude-plugin`, `.codex-plugin` and `.cursor-plugin` files use only fields their hosts still document, and the skills' frontmatter loads everywhere. The remaining work is hygiene: retire the legacy `commands/` directories, drop Claude-only frontmatter from files copied into OpenCode, and clean up wording and docs. V1 and V2 of OpenCode ship in parallel (v1.19.5 is still marked "Latest" on GitHub), so the OpenCode bridge has to detect the major version rather than assume one.

## OpenCode 2.0 rejects the bridge's `run` argv outright

OpenCode 2.0.0 was tagged on **11 September 2026**. The V2 line has reached **v2.2.6 (6 November 2026)**, while **v1.19.5 (28 October 2026) is still marked "Latest"** ([GitHub releases](https://github.com/anomalyco/opencode/releases); [v2.0.0 tag](https://github.com/anomalyco/opencode/releases/tag/v2.0.0)). Both versions install as the same `opencode` command, and the V2 curl installer replaces the V1 binary ([Migrate from V1](https://opencode.ai/v2/docs/migrate-v1/)). The V2 npm package is `@opencode/cli`, which also ships an `opencode2` alias; V1 was published as `opencode-ai`. That makes the setup hint `npm install -g opencode-ai` in `plugins/opencode/scripts/lib/opencode.mjs` and `opencode-companion.mjs` a V1-only instruction. The research notes and a local check against v2.2.6 agree that `opencode --version` prints `opencode v2.2.6`, which the bridge can parse to pick an argv shape.

The migration guide lists only three intentional breaks: the plugin API, the server/client contracts, and TUI config ([Migrate from V1](https://opencode.ai/v2/docs/migrate-v1/)). The CLI changes that hurt agent-bridges are not in that list; they show up only in the binary. Verified locally against v2.2.6 (`opencode run --help`, `opencode run --dir /tmp`, `opencode run --variant high`): **`--dir` and `--variant` both fail with `ERROR Unrecognized flag`**. `run` takes its working directory from `$PWD`/`process.cwd()`, and **`--model` now takes `provider/model#variant`**. The models docs confirm the variant syntax, warn that names such as `low`, `high` and `max` "are not available for every model", and note that variants come from each model's catalog metadata ([Models](https://opencode.ai/docs/models/)). The binary also refuses a variant with no model ("Cannot select a variant before selecting a model"). The fix for `buildRunArgs` at `plugins/opencode/scripts/lib/opencode.mjs:437` is therefore more than deleting two flags. The spawn must set `cwd`, and effort must be folded into the model reference, which means resolving a model first through the existing `getOpencodeDefaultModel` (line 133) or `opencode models`. When no model is known, the bridge should drop the effort and say so rather than fail. `--format json`, `--auto`, `-m`, `-s/--session` and `--continue` all survive unchanged.

Two V2 behaviors change how the bridge should supervise runs. Since v2.2.6, `run` **waits indefinitely for background jobs it started** and emits a `background_wait` event, the release notes admit that "CI needs a timeout", and SIGTERM now cancels the session and exits 143 ([GitHub releases](https://github.com/anomalyco/opencode/releases)). The bridge needs its own timeout and should map exit 143 to "cancelled". The same release adds `--archived`, which keeps scripted sessions out of the user's session list and is worth passing on every bridge run. Without `--auto`, V2 auto-rejects permission requests in `run`, which suits read-only reviews. The JSONL stream still uses the `{type, timestamp, sessionID, part}` envelope with `text`, `tool_use`, `step_start`, `step_finish` and `error`, and adds `reasoning`, `retry` and `background_wait`. A V1 parser keyed on `type` keeps working as long as it ignores the new types. This comes from reading the compiled emitter: no official schema page exists, and an unverified secondary source says 2.1 changed the event contracts again ([qcode.cc](https://qcode.cc/de/opencode-2-1-breaking-changes)). Treat the parser as fragile and test it against real V2 output.

Session transfer is the most exposed path. **Top-level `opencode export` and `opencode import` are gone in V2.** The local binary reads `export` as a directory argument and fails with ENOENT. Its replacements are `opencode session export [<id>] [--sanitize]` and `opencode session import <file|URL> [--directory <dir>]`, which the local `opencode session --help` confirms. `plugins/opencode/scripts/lib/transfer-dest.mjs` lines 47 and 63 still call `["import", tmpFile]`. Renaming the subcommand is necessary but probably not sufficient. The import payload is a hand-built `{role, content}` messages array, V2 documents no export schema, and the server message contracts changed ([Migrate from V1](https://opencode.ai/v2/docs/migrate-v1/)). The safe path is to capture a real `opencode session export` from V2, use it as a fixture, and treat transfer into OpenCode as unsupported on V2 until it round-trips.

## The OpenCode installer writes into directories V2 reinterprets

`scripts/lib/opencode-install.mjs` (`resolveInstallPaths`) targets `~/.config/opencode/` or `<project>/.opencode/`, and **both roots remain valid in V2** ([Migrate from V1](https://opencode.ai/v2/docs/migrate-v1/)). The subdirectories are the issue. The installer writes `command/` and `agent/`. V2 still discovers those as legacy names, but the docs say to "use `commands/` for new files" and to prefer `agents/<name>.md` ([Commands](https://opencode.ai/docs/commands/); [Agents](https://opencode.ai/docs/agents/)). Switching to the plural names, and removing the old files on reinstall (the manifest-driven cleanup already exists), is a small change. It doesn't break anything today, but it heads off a future removal.

The larger risk is `pluginTree`. The installer `cpSync`s the whole `plugins/<name>` source, including its `package.json`, into `<root>/plugins/<name>/`. In V2, **"immediate package directories are auto-loaded"** from every discovered `.opencode/plugins/` and from `~/.config/opencode/plugins/` ([Plugins](https://opencode.ai/docs/plugins/)). A V2 plugin is an ES module exporting `Plugin.define({id, setup})` from `@opencode/plugin`, and "V1 plugin implementations don't run in V2" ([Build a plugin](https://opencode.ai/docs/build/plugins/); [Migrate from V1](https://opencode.ai/v2/docs/migrate-v1/)). The agent-bridges tree exports nothing of the kind. The docs don't say whether OpenCode logs a load error or silently skips such a directory, so the outcome is uncertain, but the directory looks like a plugin package to the loader. The fix that preserves today's design is to store the companion tree outside the auto-load path, for example `~/.local/share/agent-bridges/<name>` or `<root>/agent-bridges/<name>`, and to move `marketplace-installed.json` with it. Every `SKILL.md` lists `~/.config/opencode/plugins/<name>` as a `<plugin-root>` candidate, so those lists must change too. Installs can rely on the installer's own rewrite of `<plugin-root>`, but the hard-coded fallback line is in 40 of the 44 skill files.

Skills need less work. V2 reads `skills/<id>/SKILL.md` from the OpenCode roots and also, natively, from `~/.claude/skills`, `.claude/skills` and `.agents/skills` ([Skills](https://opencode.ai/docs/skills/)). OpenCode advertises a skill only if it has a `description`, takes the ID from the directory, treats `name` as a label, and honors `disable-model-invocation` and `metadata`. It accepts `license` and `compatibility` without interpreting them, and it doesn't document `allowed-tools` or `user-invocable`, which it most likely ignores. Every repo skill already has a `description` and a directory-matching name, so skills install cleanly. The docs don't define precedence when the same skill ID appears in several roots. That matters only if a user also places these skills in `~/.claude/skills`. Claude Code plugin installs live under `~/.claude/plugins/` and don't collide.

The OpenCode docs don't explicitly answer one installer question: whether V2 maps the V1 `plugin` config key to `plugins`. The README states that the installer "does not add entries to `opencode.json` `"plugin": []`". That line should name the V2 key `plugins` so readers don't edit the wrong one. A native V2 plugin package that registers commands and agents through `setup(ctx)` is possible, but it would tie the repo to an API that has changed in three of the six 2.2.x releases listed (v2.2.1, v2.2.3, v2.2.4, per [GitHub releases](https://github.com/anomalyco/opencode/releases)). Plain markdown files remain the lower-maintenance choice.

## Copied frontmatter is mostly inert on OpenCode, with two exceptions

The installer copies Claude-flavored command and agent files into OpenCode verbatim, apart from the `<plugin-root>` rewrite. V2 command frontmatter honors only `description`, `agent`, `model` (`provider/model[#variant]`) and `subagent` (with `subtask` as a deprecated alias). The name comes from the filename, and the body is the template, with `$ARGUMENTS` and `$1..$n` placeholders ([Commands](https://opencode.ai/docs/commands/)). The repo's `name`, `argument-hint`, `disable-model-invocation` and `allowed-tools` keys are undocumented there and appear to be ignored. In practice, **the `allowed-tools: Read, Glob, Grep, Bash(node:*), Bash(git:*)` restriction on `plugins/opencode/commands/review.md` applies only in Claude Code**, so on OpenCode the review command inherits the session's normal permissions. `$ARGUMENTS` survives, so the commands themselves still work.

Agents are where the copy really breaks. V2 agent frontmatter is `description`, `mode`, `model`, `permissions` (an ordered `{action, resource, effect}` list), `steps`, `hidden`, `color`, `disabled` and `request`, with the body as the system prompt. The docs list `tools`, `permission`, `prompt` and `maxSteps` as legacy ([Agents](https://opencode.ai/docs/agents/)). `plugins/opencode/agents/opencode-rescue.md` and its siblings carry `model: sonnet`, `tools: Bash` and `skills:`. `tools: Bash` is legacy-normalized at best, and `Bash` maps to the V2 action `shell` ([Migrate from V1](https://opencode.ai/v2/docs/migrate-v1/)). **`model: sonnet` is not a `provider/model` reference**, so an OpenCode run of that agent can fail model resolution. `skills:` isn't an OpenCode field. When installing agents, the installer should drop `model`, `tools` and `skills`, or replace them with `mode: subagent` plus a `permissions` list that allows `shell`. It also has to rename the file from `opencode--opencode-rescue.md` if a clean ID matters: V2 derives agent IDs from the path, so the installer's `<plugin>--` prefix becomes part of the ID, as it does for commands (`/opencode--review`). That naming is deliberate and harmless, but the README should document it. V2 also reads `AGENTS.md` and **no longer reads `CLAUDE.md`** ([Migrate from V1](https://opencode.ai/v2/docs/migrate-v1/)), which matters only if docs tell OpenCode users to rely on `CLAUDE.md`.

## Claude Code, Codex and Cursor need small fixes; Antigravity needs one flag fix

On **Claude Code (2.1.319)** every manifest field the repo uses is still valid. The repo's hooks files use the required top-level `"hooks"` wrapper and quote `"${CLAUDE_PLUGIN_ROOT}"`, as `validate` expects ([plugins-reference](https://code.claude.com/docs/en/plugins/manifest-reference)). The real bug is in the backend. `--json-schema` takes **inline JSON only**, and a path fails with `Error: --json-schema is not valid JSON` (tested locally in the notes; the docs show only inline examples per [cli-reference](https://code.claude.com/docs/en/cli-reference)). `plugins/claude/scripts/lib/claude.mjs:66` passes `options.schemaPath`, and `claude-companion.mjs:254` sets that to `schemas/review-output.schema.json`, so every structured Claude review hits this error. The fix is to read the file and pass its contents, then check that `structured_output` is present before using it, because the field is absent when the run ends without valid output ([headless](https://code.claude.com/docs/en/headless)). The rest of the argv already matches current behavior. `-p` has started in Manual mode since v2.1.302, and the bridge always passes `--permission-mode plan` or `--dangerously-skip-permissions`. `--bg` is never combined with `-p`, which is forbidden. Effort values `low|medium|high|xhigh|max` are accepted ([cli-reference](https://code.claude.com/docs/en/cli-reference)). The forward-looking change is the commands-to-skills merge in v2.1.3. The docs now say **"Prefer `skills/` for new plugins"** and the CHANGELOG calls command files "legacy" ([skills](https://code.claude.com/docs/en/skills); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). The `claude` plugin already ships skills only. The `commands/` directories in `cursor`, `gemini` and `opencode` duplicate their skills and can retire once the OpenCode installer generates commands from skills, or drops them. Plugin agents ignore `hooks`, `mcpServers` and `permissionMode` ([sub-agents](https://code.claude.com/docs/en/sub-agents)), and the repo's agents set none of them. One more recommendation: `claude plugin validate --strict` skips component files on a marketplace run, so CI should validate each `plugins/<name>` separately ([plugins/cli-reference](https://code.claude.com/docs/en/plugins/cli-reference)).

On **Codex (0.167.0)** the marketplace at `.agents/plugins/marketplace.json`, the `.codex-plugin/plugin.json` fields, `codex plugin marketplace add`, `codex plugin add name@marketplace`, and the `PLUGIN_ROOT`/`CLAUDE_PLUGIN_ROOT` hook variables are all still documented ([Codex: Build plugins](https://developers.openai.com/codex/plugins/build); [plugin-json-spec](https://raw.githubusercontent.com/openai/plugins/main/.agents/skills/plugin-creator/references/plugin-json-spec.md)). Codex plugins document no `commands` or `agents` component, so on Codex the skills are the whole product, which the README already reflects ([Codex: Plugins](https://learn.chatgpt.com/docs/plugins)). Codex documents those env vars only for hooks, so the skills' habit of falling back across several candidate roots, instead of trusting `$PLUGIN_ROOT`, is the right defensive design. The only edit needed is wording: `plugins/cursor/.codex-plugin/plugin.json` line 12 still says "existing cursor-agent install", and the documented binary is `agent`.

On **Cursor** the plugin manifest documents no `displayName` field ([Cursor: Plugins reference](https://cursor.com/docs/reference/plugins)), so `plugins/*/.cursor-plugin/plugin.json` carries an undocumented key that Cursor most likely ignores. Drop it unless a validator wants it. Cursor reads `.claude/skills`, `.codex/skills` and `.agents/skills` ([Cursor: Skills](https://cursor.com/docs/context/skills)), and it is moving slash commands into skills with `disable-model-invocation: true`, the same direction Claude Code is taking. On the backend, every Cursor Agent CLI flag the bridge uses (`-p`, `--mode plan`, `--force`, `--trust`, `--model`, `--resume`, `--output-format`) is current ([Cursor CLI parameters](https://cursor.com/docs/cli/reference/parameters)). The parser should treat a non-zero exit with no JSON object as failure, because Cursor emits no JSON on error ([Cursor CLI output format](https://cursor.com/docs/cli/reference/output-format)).

On **Gemini CLI (0.67.0) and Antigravity `agy` (1.5.3)**, the `gemini` argv needs no changes: `--approval-mode=plan`, `-r latest`, `--skip-trust` and `--include-directories` are all valid. Gemini CLI also stopped serving free and AI Pro/Ultra individual users on **18 June 2026** ([Google Developers Blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)), and setup should tell those users so. The agy branch has one bug. `plugins/gemini/scripts/lib/gemini.mjs:523-525` appends `--include-directories a,b` after the backend branch, so agy receives it, but **agy's flag is a repeatable `--add-dir`** (from `agy --help`). Move it inside the gemini branch and emit `--add-dir <d>` per directory for agy. Two agy behaviors need to reach the bridge's result handling. First, a `--print-timeout` expiry now exits with **code 3** and sets `finished_reason: "print_timeout"`, so it should be reported as partial rather than success. Second, `--dangerously-skip-permissions` now blocks denylisted commands ([agy headless](https://antigravity.google/docs/cli/headless/)). Read-only agy reviews pass no mode, so write tools are only soft-denied and the run exits 0. Adding `--mode plan` is the natural equivalent of Gemini's `plan`, but no one has verified it headless. Unauthenticated agy also waits about 60 seconds on an OAuth prompt before failing, so the setup auth probe needs a short timeout.

## Conclusion

Most of the drift happened in CLIs, not manifests. Every host kept its plugin manifest backward compatible, but OpenCode, Claude Code and Antigravity each changed command-line behavior in ways their changelogs only partly announce. The OpenCode `--dir`/`--variant` removal, for example, appears in no migration document and was found only by running the binary. The repo's unit tests check argv arrays against expectations written by hand, so they would not catch this kind of break. The highest-leverage durable change is a cheap smoke test per backend that runs `<cli> --help` or a dry-run parse against the installed binary and fails on unrecognized flags. OpenCode needs the most care because V1 and V2 coexist and V2's plugin and event contracts are still moving. The bridge should branch on `opencode --version`, keep its install footprint to plain markdown outside the plugin auto-load directory, and treat session import as unsupported until it round-trips against a real V2 export.

All four hosts are also converging on one portable unit: a `skills/<id>/SKILL.md` directory with `name` and `description`, discovered from `.agents/skills` or `.claude/skills`. Commands are legacy in Claude Code, absent in Codex, being migrated in Cursor, and need conversion to TOML for Gemini extensions. Antigravity offers `agy plugin import claude` ([agy plugins](https://antigravity.google/docs/plugins/)), which means a well-formed Claude plugin is effectively a universal source format. Making skills canonical and generating any host-specific command files from them removes a whole class of per-host compatibility work.
